# Avito Search Relevance

Поиск релевантных объявлений по текстовому запросу — тестовое задание на стажировку **Avito DS Bootcamp**.

**Финальный результат: Recall@50 = 0.7745** (тестовый набор)

## Задача

Для каждого поискового запроса вернуть топ-50 наиболее релевантных объявлений из каталога. Метрика — Recall@50, усреднённая по запросам.

## Архитектура

```
Запрос ──┬── BM25 (лексический поток) ──────── top-200 ──┐
         │                                               ├── Weighted RRF ── top-50
         └── Bi-Encoder ruBERT (dense поток) ── top-200 ──┘
```

Два независимых потока извлекают кандидатов из каталога: лексический (BM25) и нейросетевой (Bi-Encoder, дообученный `rubert-tiny2`). Результаты объединяются через Weighted Reciprocal Rank Fusion. Каждый поток применяет двухуровневый фильтр по городу и категории.

## Результаты

| Метод | Recall@50 (валидация) | Recall@50 (тест) |
|---|---|---|
| BM25 (обогащённый текст + стемминг) | 0.6330 | — |
| Bi-Encoder (rubert-tiny2, 4 эпохи) | 0.6580 | — |
| **Weighted RRF (BM25 + Bi-Encoder)** | **0.7057** | **0.7745** |

Разрыв между валидацией и тестовым набором объясняется разницей в размере каталога (344 825 vs 189 212 объявлений) — подробнее в ноутбуке, раздел 8.

Полный разбор ошибок — распределение recall по запросам, вклад каждого потока, кросс-городская релевантность — в разделе 6 ноутбука.

## Описание решения

**Данные и признаки.** Использованы `item_title_raw`, `item_infm_params_text` и `item_description_raw` как основной текстовый сигнал (семантика объявления), `item_location_id` и `item_category_id` — для фильтрации кандидатов по городу/категории, `search_is_delivery_search` — флаг, отключающий привязку к городу для доставки. Подробное обоснование — в разделе 1 ноутбука.

**Модели и алгоритмы.** Два независимых потока извлечения кандидатов — BM25 (лексический, с русским стеммером) и дообученный Bi-Encoder на базе `rubert-tiny2` (нейросетевой, по косинусному сходству). Результаты объединяются через Weighted Reciprocal Rank Fusion (RRF), без обучения. Разделы 3–5 ноутбука.

**Как проверялось качество до отправки.** 80/20 сплит по уникальным поисковым запросам (без утечки — один запрос не попадает одновременно в train и val). Recall@50 замерен отдельно для BM25, Bi-Encoder и итогового RRF на валидации, чтобы убедиться, что объединение потоков действительно даёт прирост (0.6330 / 0.6580 → 0.7057), а не просто добавляет шум. Раздел 2 и таблица результатов выше.

**Анализ ошибок и что было сделано.** Разобраны: распределение recall по запросам (16.2% запросов с нулевым recall — основной резерв роста), кросс-городская релевантность (87.7% релевантных объявлений — в том же городе), вклад каждого потока в покрытие ground truth и находка о том, что категория в датасете почти не варьируется (99.95% запросов — одна категория), из-за чего фильтр по категории почти не работает как дискриминирующий признак — вся полезная нагрузка на локации. На основе этого отклонён CatBoost re-ranking (не окупал затраты GPU-памяти ради +0.01 Recall@50). Полный разбор — раздел 6 ноутбука.

**Воспроизводимость.** Все источники случайности (`random`, `numpy`, `torch`, включая cuDNN) фиксируются через `seed_everything(42)`. Обучение Bi-Encoder идёт в FP16 (Mixed Precision) — это не гарантирует 100% побитовую детерминированность на GPU, поэтому при повторном запуске Recall@50 может отличаться от заявленного в пределах ~0.001–0.002. Итоговый пайплайн (загрузка данных → BM25 → Bi-Encoder → RRF → `answer.csv`) выполняется от начала до конца без ручных вмешательств.

## Как запустить

1. Клонировать репозиторий и установить зависимости:

   ```bash
   git clone https://github.com/<ваш-юзернейм>/avito-search-relevance.git
   cd avito-search-relevance
   pip install -r requirements.txt
   ```

2. Положить `train.parquet`, `benchmark_items.parquet`, `benchmark_queries.parquet` в папку `data/` (не включена в репозиторий, см. `.gitignore`).

3. Открыть `notebooks/pipeline.ipynb` и выполнить ячейки по порядку — ноутбук строит BM25-индекс, дообучает Bi-Encoder, объединяет потоки через RRF, проводит анализ ошибок и формирует `answer.csv` для сабмита.

## Ключевые технические решения

- Обогащение текста документа (заголовок ×3 + параметры + описание) заметно улучшает BM25 по сравнению с наивным подходом.
- RRF строит финальный топ-50 из топ-200 кандидатов каждого потока, а не из их топ-50 — именно за счёт этого объединение даёт устойчивый прирост над каждым потоком по отдельности (0.6330 / 0.6580 → 0.7057).

## Возможные улучшения

- Более крупная dense-модель (rubert-base, 180M параметров) при наличии ресурсов.
- Cross-Encoder re-ranking поверх RRF-кандидатов для финального переупорядочивания.
- Hard negative mining при обучении Bi-Encoder.
- Ослабление ярусного фильтра для кросс-городских запросов.
